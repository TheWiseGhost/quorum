# Bugs caught by the test harness

Every real bug the crash tests or the simulator found during development: how it was found, the root cause, and the fix.

| # | Found by | Symptom | Root cause | Fix |
|---|----------|---------|------------|-----|
| 1 | `CrashRecoveryTest` (SimFileSystem power loss), 32 of 40 seeds | After a crash, reopening failed with `FileNotFoundException: db/000040.sst` | A flush or compaction fsynced the new SSTable's *contents* and the MANIFEST record, but never the *directory entry* for the new file. On POSIX file systems a newly created file's name is not durable until its parent directory is fsynced, so the MANIFEST could name a table that no longer existed after the crash. | `VersionSet.logAndApply` fsyncs the database directory before appending the MANIFEST record. |
| 2 | `RaftStorageTest` crash sweep, 20 of 20 seeds | After a follower overwrote a conflicting log suffix and then crashed, recovery lost dozens of *fsynced* entries | `truncateFrom` reopened the segment and built its `LogWriter` *before* truncating the file. The writer cached the old file size as its append offset, so new records landed after a hole of zeros. Recovery read the zeros as a torn frame and dropped everything after them. | Truncate and fsync first, then construct the writer at the real end of the file. |
| 3 | Simulator (seeds 5 and 14 of the first 40-seed sweep): crash + Raft snapshots | A follower that installed a leader snapshot hit `FileNotFoundException: kv/data-000003/000027.sst` during compaction | Two flaws together. (a) `LsmEngine.checkpoint` opened `MANIFEST-000001` in the target directory with create-or-open and appended, so a stale manifest left by a checkpoint interrupted by a crash got the new edits appended after it. The restored engine then believed in tables that were never shipped. (b) The simulated disk revived files whose unlink was not yet durable but forgot their parent directory, so the cleanup (`deleteRecursively` on `snap-tmp`) could not see the leftovers. | Checkpoints refuse a non-empty target and truncate the manifest before writing. `SimFileSystem` treats any surviving file's parent as an existing directory. |
| 4 | Simulator, planted-bug sweep (seed 165): **replica divergence**. Two followers at the same applied index held different values for `k1`. Reproduced in isolation by `CrashRecoveryTest` once background work was deferred (22 of 60 seeds). | After a crash, the LSM engine recovered a state that was not a prefix of the write history | On memtable rotation the old WAL was closed **without fsync** and writes went to a new WAL. Unsynced data in two different files can be lost independently, so a crash could keep a later batch (new log) and drop an earlier one (old log). The KV state machine writes with `sync=false` and relies on the engine recovering an exact prefix (the Raft log replays the rest), so the replica silently diverged. The original crash test missed this because it ran flushes inline, which closed the window. | `makeRoomForWrite` fsyncs the old WAL before switching. The crash test now defers background work to random points, as the simulator does. |
| 5 | `ClusterIntegrationTest` (real sockets, leader killed and restarted 3 times under load) | After a restart, every node sat in `PRE_CANDIDATE` and the restarted node never received another message | `NioPeerTransport.close()` closed the listening socket and outbound connections, but not the inbound connections it had *accepted*. Closing a `Selector` only deregisters its channels. Peers kept a healthy-looking TCP connection to the dead incarnation and wrote into a socket nobody read, while the restarted node waited for traffic that never came. This is also a file-descriptor leak in production. | Close every registered channel on shutdown. |
| 6 | Simulator, 10,000-seed sweep after a performance change: 8 failures, all with membership churn + crashes, including **two leaders in one term** (Election Safety) and a leader missing committed entries | Restarted nodes acted on a configuration several membership changes out of date | A regression introduced by my own optimization. To save two fsyncs per batch, the commit index stopped being persisted (term and vote still were). But a restarting node rebuilds its membership by replaying conf-change entries *up to the persisted commit index*, so it could come back with a configuration several changes old. Single-server membership changes are safe only because consecutive configurations have overlapping majorities; that argument fails across several steps, and two disjoint "majorities" each elected a leader in the same term. The earlier 5,000-seed sweep (before the optimization) was clean, which pointed straight at the change. | Keep skipping commit-only writes, but persist the hard state whenever a batch commits a conf-change entry. A restarted node is then at most one configuration behind, which the overlap argument covers. All 8 seeds pass, and a 20,000-seed rerun is clean. |
